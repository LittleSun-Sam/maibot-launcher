# 更新日志怎么写（发布约定）

启动器「检查更新」的二级窗口**直接显示这段文字**，窗口很小：写长了用户不看，也没地方看。
所以「短」是硬要求，不是风格偏好。

## 一、固定结构（四节，顺序不可变）

```
## 新增功能
## 优化微调
## 即将更新
## 删除内容
```

- 某节这次没有内容 → 写「无」，**不要删掉标题**（结构稳定，用户扫一眼就知道去哪找）。
- 每节 1~6 条，一条一行，20 字以内。
- 「即将更新」只写**已经确定要做**的事，不写愿景、不写"可能"。

## 二、内容要求

- 只写**用户能感知的变化**。文件名、函数名、内部报错、根因分析、重构过程一律不写，
  那些留在 git 提交记录里。
- 措辞通用化：改了哪个页面就写那个页面，不写"某某模块的某某逻辑"。
- 「删除内容」要如实写**移除了什么**（界面上消失的入口、按钮、功能都算），
  用户找不到东西时会来这里查。
- 结尾固定一句，不额外发挥：`运行安装包即可完成升级，配置与数据会保留。`

## 三、什么时候提交 / 发布

**只有用户明确说"提交"或"发布"时才 commit、push、发 Release。**
平时改完就留在工作区里等指示，不自作主张提交。

## 四、模板

```
## 新增功能
- ……
- ……

## 优化微调
- ……
- ……

## 即将更新
- ……

## 删除内容
- ……

运行安装包即可完成升级，配置与数据会保留。
```

## 五、反面例子（不要这样写）

- 写成十几条、每条几十字，把根因和文件名都塞进去；
- 写成"修正某文件缺分号导致枚举恒失败"这种只有作者看得懂的句子；
- 通篇"重构 / 优化内部实现"，用户读完不知道有没有自己关心的东西；
- 四节里少写一节，或把「即将更新」写成许愿清单。
